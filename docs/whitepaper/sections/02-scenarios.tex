\section{典型场景}

下面四个场景都来自漫展/晚会期间真实发生过的尴尬瞬间。每个场景说一下平时怎么走、用\,\app\,会怎么走。

\subsection{场景 A · 漫展开/闭幕式}

\textbf{现状。} 主持人在台前串场,PPT 跑在后台机器上由工作人员盯翻页。每次主持人说"下一页",工作人员要等 0.5\,$\sim$\,1.5\,s 才确认动作,节奏被拖住;主持人讲一段又得回头看后台是否跟上。

\textbf{用\,\app。} 主持人手机扫码,ARM 之后用一个全屏大按钮翻页(底栏占满整个手指能到的区域,单手大拇指可按)。下一页延迟 $\sim$\,30-80\,ms,主持人不再回头看后台。后台导播可同时看到当前页 + 状态,有问题随时\role{紧急锁}。

\textbf{典型流程。} 开幕前导播打开远控 → 主持人扫码 ARM → 开幕进行中只翻页 → 节目穿插期间不动 → 结束后导播\role{关远控}。

\subsection{场景 B · 互动答题 / 投票环节}

\textbf{现状(元火做法)。} PPT 内嵌"四选一"按钮(VBA 宏触发)。一般翻页器只能"上/下页",触发不了这种按钮。元火现在的做法是:观众抢答后告诉主持人,主持人对着麦克风复述选项 A/B/C/D,演播室里的导播听见再去鼠标点 PPT 上的按钮。两次人工传话,主持人和导播都在紧绷,任何一环走神节奏都掉。

\textbf{用\,\app。} \app\ 自动检测当前幻灯片上所有绑定了\,\texttt{ppActionRunMacro}\,的形状,把它们的名字推到主持人页 —— 比如 "选项 A" / "选项 B" / "公布答案" 直接出现在主持人界面上,2 列大按钮排好。主持人在台前自己点哪个就触发哪个,演播室那边变成只看不动。原本要三个人配合的环节,变成主持人一个动作。

\begin{infobox}
\textbf{技术细节}:形状 → 宏 的绑定关系由 \app\ 服务端实时从 PowerPoint 读出,主持人端只能看到\textit{形状名字}发回服务端,真正的宏调用由服务端再次查询 \texttt{ActionSettings(ppMouseClick).Run} 完成。即使主持人页被监听,也无法借此触发任意宏。
\end{infobox}

\subsection{场景 C · cosplay 大赛评分公布}

\textbf{现状。} 评委评分结束,主持人在台上准备公布前几名。后台工作人员要在 PPT 上一页页翻、找到对应排名页、按节奏推进。评分到颁奖的几分钟里,工作人员压力陡增,容易翻错页。

\textbf{用\,\app。} 评分 PPT 提前准备好按排名分页(第 1 名、第 2 名、第 3 名 …)。主持人在台上每念一个名字之前自己翻到对应页;后台导播全程只盯画面是否正确,出错可立即\role{回到上一页}或\role{黑屏}重整节奏。

\subsection{场景 D · 多段节目串场报幕}

\textbf{现状。} 漫展通常 10$\sim$15 个节目穿插,每个节目前要报幕、念赞助、放预告片。报幕员经常是不同的人,工作机和翻页器不能跟着报幕员换手。

\textbf{用\,\app。} 不同的报幕员各自扫一次码,导播这边可随时\role{收回 ARM}让控制权移交给下一位主持人。整场只有一台后台机器,不需要切设备;扫码一次的人不需要装任何 App,演出结束直接关浏览器走人。

\begin{infobox}
\textbf{操作模型}:任意时刻只有最近一次 ARM 的主持人能下指令,导播 GUI 里也能看到当前主持人的简短标识。"上一个报幕员还没正式交接、下一个就抢动作"这种情况不会发生 —— 不是靠人沟通靠住的,是流程上就不让它发生。
\end{infobox}

\subsection{前提:PPT 需要 VBA 化才能用上互动按钮}
\label{sec:vba-prerequisite}

上面的场景 B(答题)和场景 C(评分公布)依赖一个前提:PPT 文件本身得是\,\texttt{.pptm}\,格式,互动按钮要绑 VBA 宏。\app\ 是直接接 PowerPoint COM 触发宏,如果幻灯片上只是放了个"形状"没绑动作,主持人页中间区域就是空的 —— 不是\,\app\,检测不到,是 PPT 本身就没那个交互。

这件事\,\app\,没法替你做。但据我们了解,元火本来就在推"幻灯片整体 VBA 化"的工作流(漫展互动答题、抽奖、票选这类节目本来就需要 VBA 才能搞),所以是顺水推舟,不算额外负担。具体怎么绑宏(\,\texttt{.pptm}\,格式 / \,\texttt{ActionSettings → Run Macro}\,/\,签名信任\,)\,\app\ 项目组可以提供模板和现场支持。

\textbf{兜底路径:视觉 + 模拟鼠标点击(不推荐)。}\,\app\,还支持另一条互动路径\,—— 主持人在手机上看 PPT 当前幻灯片的实时缩略图,用手指戳哪儿,后台 Win32 就在对应屏幕坐标上模拟一次鼠标点击(走\,\texttt{/api/click}\,端点,坐标归一化在\,$[0,1]^2$\,)。这条路在 PPT 没绑宏的情况下也跑得通,但有几个真实的问题:

\begin{itemize}
  \item 主持人需要在 6\,英寸手机屏上精确戳到舞台大屏上一个按钮的相对位置,误差容忍度低,台上紧张时容易戳偏。
  \item 画面是 MJPEG 推流,有 100-200\,ms 延迟。主持人看到的"现在"实际是过去时,按钮位置有可能已经动了。
  \item PPT 排版一改、按钮位置一动,主持人手感全部归零;同样的 PPT 不同分辨率显示器也会偏。
  \item 没法做"按钮名字\,$\to$\,主持人页 2 列大按钮" 这套自动 UI,主持人页就只剩翻页按钮 + 一张幻灯片预览,信息密度低很多。
\end{itemize}

兜底路径存在的意义就一句:"PPT 已经做好了,临时来不及 VBA 化"。如果还有时间从头规划演出,优先走 VBA 的正路。两条路是互补不是替代,VBA 化的 PPT 也可以临时混着用视觉点击 —— 但反之不成立。
