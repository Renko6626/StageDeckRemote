主应用进程的"两套 API,一份状态"是核心结构选择,见下。

\subsection{两套 API,一份状态}

主应用进程把导播和主持人放在两个完全不同的 surface,但底下共享同一份 \texttt{Arc<AppState>}:

\begin{itemize}
  \item \textbf{导播 = Tauri IPC}(\texttt{commands.rs})。privileged。这些命令\textit{从不绑端口},LAN 上结构性不可达。能做的事:枚举/选窗、开关远控、紧急锁、本地翻页、重置访问码、Relay 配置。
  \item \textbf{主持人 = Axum HTTP}(\texttt{routes.rs} + \texttt{web\_server.rs})。token-gated。所有路由都查 \texttt{click\_allowed = remote\_enabled \&\& !control\_locked \&\& presenter\_unlocked},任一项 false 就 403。
\end{itemize}

一个值得注意的工程后果:\texttt{routes.rs} 不依赖 \texttt{tauri} crate,可以在没有 webkit2gtk 的 Linux 上单独编译和单测。这也是 Relay 模式下,同一个 \texttt{axum::Router} 能被 Relay 客户端(\texttt{relay\_client.rs})复用的前提:Relay 收到 \texttt{TunnelReq} 后用 \texttt{tower::ServiceExt::oneshot} 把同一个 Router 当 Service 调一次,\textbf{业务路由代码零修改}就能跑在两种传输模式下。

\subsection{PowerPoint 控制:为什么是 IDispatch COM}

\texttt{ppt\_com.rs} 直接通过 COM \texttt{IDispatch} 控制 PowerPoint。两条对比方案在演出场景下都不工作:

\begin{itemize}
  \item \textbf{SendKeys / 模拟键盘} —— 只能翻页,触发不了任意 VBA 宏。漫展互动答题这类需求过不去。
  \item \textbf{Office.js add-in} —— 加载 add-in 需要签名 + 信任流程,演出当场临时装不实际。
\end{itemize}

\textbf{COM IDispatch} 是 PowerPoint 自己定义的 OLE 自动化接口,任何 \texttt{.pptm} 都吃,不需要改 PPT,不需要签名,接口稳定多年。\app\ 通过 \texttt{GetActiveObject("PowerPoint.Application")} 拿到\,application 对象 —— 注意是窗口无关的(独立于截屏抓到的窗),所以即使主持人选窗选错了也不影响 PPT 控制。翻页/黑屏/恢复走 \texttt{SlideShowWindows(1).View} 的 \texttt{Next/Previous/BlackOut/NormalView}。

\textbf{宏检测}(场景 B 答题环节的底层):枚举当前幻灯片所有 \texttt{Shape},对每个读 \texttt{ActionSettings(ppMouseClick).Action};\texttt{== 8} 表示 \texttt{ppActionRunMacro},再读 \texttt{.Run} 拿到宏名。结果 \texttt{Vec<(shape\_name, macro\_name)>} 推给主持人页,主持人页只显示 \texttt{shape\_name}(选项 A / 选项 B 等),不暴露宏名。触发时主持人发回 \texttt{shape\_name},服务端\textit{再读一次} \texttt{ActionSettings.Run} 拿当时绑的宏调用 —— \textbf{不信任客户端发回的宏名},也就消除了"如果有人嗅探了 token 能不能借此触发任意宏"的风险。

\textbf{VARIANT 类型萃取的一个关键细节}:PowerPoint 返回值大多是 \texttt{VT\_DISPATCH (9)} 包着 \texttt{IDispatch} 指针。从 \texttt{VARIANT} 萃取对象\textbf{必须}用 \texttt{IDispatch::try\_from(\&VARIANT)},不能用 \texttt{IUnknown::try\_from(\&VARIANT)} —— 后者对 \texttt{VT\_DISPATCH} 的解引用是错的,拿到的指针在第一个 \texttt{Invoke} 调用上会炸。\texttt{ppt\_com.rs} 顶端有注释提醒。

\subsection{截图与推流:变化驱动 + Broker 扇出}

主持人页和导播 GUI 都要看到 PPT 当前画面。\app\ v0.1.16 起的方案(ADR-0006):

\begin{lstlisting}
WGC 后台会话(capture_session.rs)
  └→ 持续把帧 BGRA 写到 shared 内存
       └→ encoder thread 做采样 hash
           ├→ 没变 → 不编码,等下一帧
           └→ 变了 → 编码 JPEG q82 一次
               └→ frame_broker: watch::Sender<Arc<EncodedFrame>>
                   ├→ 主持人: GET /api/stream.mjpg
                   │   (multipart/x-mixed-replace,浏览器 <img> 原生消费)
                   └→ 导播 GUI: Tauri Channel<ipc::Response>
                       (二进制直接推到 webview <canvas>)
\end{lstlisting}

两个具体决定:

\textbf{采样 hash 而不是整图 hash}。整图 hash 在 1080p 上要扫 6 M 像素,~3-5 ms。采样是把屏幕切 8\,$\times$\,8 网格,只 hash 64 个像素,\,$<$\,0.1 ms。漏检率很低,因为 PowerPoint 任何"翻页 / 黑屏 / 互动按钮按下"都会改变大片区域,采样几乎必中。即使采样错过一帧,下一帧立刻补上 —— 也就 16 ms。

\textbf{\texttt{watch} 而不是 \texttt{broadcast}}。视频流场景"永远只看最新"是对的语义:慢消费者(网络差的主持人手机)掉中间帧不影响快消费者,而 \texttt{broadcast} 在慢消费者前会 lag-drop 或拖累所有人。\texttt{tokio::sync::watch::Sender} 的语义("只保留最新值,所有 receiver 各自决定何时取最新")正好匹配视频流。

实测结果:静止幻灯片 idle CPU $\approx$ 0-1\%;翻页瞬间 encoder 占一个核 \,$\sim$\,30-50 ms 完成编码。

\subsection{Relay 隧道:控制+推流分两条 WebSocket}

Relay 架构(ADR-0007)的核心选择是\textbf{把控制信道和推流信道拆成两条独立 WS}。

\textbf{控制 WS}(\texttt{/director/control}):

\begin{enumerate}
  \item 导播首帧发 \texttt{ClientHello \{session\_id, token, secret, version\}}。Relay 校验 sid 格式 + secret 一致(允许同 secret 重连接管),回 \texttt{ServerHello \{ok, reason\}}。
  \item 之后是双向消息流。Relay 收到主持人 HTTP 请求,封装成 \texttt{TunnelReq \{req\_id, method, path, query, headers, body\_b64\}} 经控制 WS 反向打给导播。导播在内部通过 \texttt{tower::ServiceExt::oneshot} 把这个请求喂给自己的 \texttt{axum::Router}(就是 LAN 模式下听 8787 的同一个 Router),拿到响应封成 \texttt{TunnelResp} 回送。Relay 拆开 \texttt{TunnelResp} 再返回给主持人 HTTP 连接。
  \item 心跳:\texttt{Ping/Pong} 配合 60s 宽限期。控制 WS 断开 60s 内重连 = 接管(session 状态保留);超时 = 后台 reaper 摘掉 session。
\end{enumerate}

\textbf{推流 WS}(\texttt{/director/stream}):

\begin{enumerate}
  \item 同样的 ClientHello / ServerHello 握手。
  \item 之后是单向流:导播 subscribe 自己的 \texttt{frame\_broker},每次 watch 触发就 \texttt{ws.send(Binary(jpeg\_bytes))} 一帧。
  \item Relay 收到 binary 帧,推给自己的 watch,主持人端的 \texttt{multipart/x-mixed-replace} 流再分发。
\end{enumerate}

\textbf{为什么分两条 WS,不混一条}:控制信道是小帧(JSON,几百字节)、频繁、需要严格 ordering;推流信道是大帧(JPEG q82,50-200 KB)、可丢、要尽可能不阻塞控制信道。混一条 WS 的话,翻页指令会排在大推流帧后面,翻页延迟无法保证。分两条之后,翻页响应基本只受 RTT 限制,与画面流量无关。

\subsection{并发模型:tokio + spawn\_blocking 边界}

整个进程跑 tokio 多线程 runtime。但 PowerPoint COM 调用是\textbf{同步阻塞}的,而且有些(\texttt{Application.Run})可能阻塞数百毫秒。直接在 async handler 里调会卡 tokio worker —— worker 数量有限,几个 stuck COM 调用就让整个 HTTP 服务停摆。

\textbf{规则}:\texttt{routes.rs} 里所有触发 COM 的 handler 都包 \texttt{tokio::task::spawn\_blocking},把 COM 调用挪到 blocking 线程池:

\begin{lstlisting}
async fn next(State(state): State<Arc<AppState>>) -> Response {
    if !state.click_allowed() { return StatusCode::FORBIDDEN.into_response(); }
    let res = tokio::task::spawn_blocking(move || {
        ppt_com::next_slide()
    }).await;
    ...
}
\end{lstlisting}

WGC 截图也类似 —— 抓窗的同步调用走 \texttt{spawn\_blocking}。tokio worker 留给 async I/O(HTTP 路由、Relay WS、Channel 推帧),不让任何 COM 或截图调用占着 worker 不放。

\textbf{锁}:\texttt{AppState::lock()} 是统一的 helper,处理 \texttt{std::sync::Mutex::lock()} 的 \texttt{PoisonError}:锁中毒时记日志后取 inner 继续用(\texttt{into\_inner()})而不是 panic。所有锁点必须走这个 helper,代码里不应该出现裸的 \texttt{.unwrap()} / \texttt{.expect()} —— 中毒一次整个 \texttt{AppState} 不可用,演出当场没救。

\subsection{测试与跨编译}

仓库一共 49 个单元/集成测试:protocol 3 个(\texttt{ControlMessage} 序列化往返)、relay 14 个(session 注册/重连/宽限过期、admin 渲染、e2e tunnel)、stagedeck-remote 32 个(锁谓词、归一化→屏幕坐标、宏名解析、窗口排序、log ring、Relay 解码等纯逻辑)。Linux 一次 \texttt{cargo test --workspace} 全跑通 \,$\sim$\,2 秒。

\textbf{纯逻辑可单测,Windows-only 模块靠跨编 + 真机验证}。COM、WGC、SendInput 这些只有在 Windows 上才有真实现,Linux 上是 \texttt{\#[cfg(not(windows))]} 桩。所以涉及这些模块的 PR 的最低验证标准是:\,(1) 仓库根 \texttt{cargo test --workspace} 全绿;(2) \texttt{cargo xwin build --target x86\_64-pc-windows-msvc} 0 errors;(3) 至少一次 Windows 真机运行验证。前两条 Linux 主机就能做(配合 \texttt{cargo-xwin}),只有第三条需要真 Windows 机器。
