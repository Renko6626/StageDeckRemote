# ADR-0005：MVP 截图用 HTTP 轮询 + 占位图先打通链路

- 状态：Accepted（2026-06-14）
- 相关：[architecture.md §4.1/§10](../architecture.md)、[project.md §9.3/§15](../project.md)

## 背景

"手机看到画面"是核心链路，但实时画面传输方案众多（轮询、WebSocket、MJPEG、WebRTC），
复杂度差异巨大。同时真实 Win32 截图尚未实现。MVP 阶段需要用最低复杂度先把端到端链路跑通，
再逐步提升画质/帧率。

## 决策

- 传输：MVP 用 **HTTP 轮询** `GET /api/snapshot.jpg`，前端**链式刷新**（上一帧 `load`/`error`
  后再排下一帧，间隔 ≥300ms ≈ 3fps），避免慢链路下请求堆积。
- 内容：`capture.rs` 当前返回**占位 JPEG**（未选窗口时也给图），使链路在任何平台可联调；
  真实截图在 `#[cfg(windows)]` 分支以 `TODO(windows)` 待填。

## 影响

**正面**
- 复杂度最低，先验证"截图→显示→点击→真实点击"闭环是否成立。
- 占位图让前端、坐标映射、三层锁、点击路径都能在没有真实截图时先联调与评审。

**负面 / 代价**
- 轮询带宽/延迟不如推流；帧率受限。
- 占位图不是真实画面，真实截图实现前不能做现场验收。

## 备选方案

- **一开始就上 WebRTC**：画质/延迟最好，但复杂度过高，[project.md §9.3](../project.md) 明确不建议 —— 暂否。
- **WebSocket / MJPEG 推流**：是 P1+ 的演进方向，链路稳定后再上 —— 推迟，不在 MVP。
