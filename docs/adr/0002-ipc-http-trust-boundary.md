# ADR-0002：导播走 IPC、主持人走 HTTP 的信任边界

- 状态：Accepted（2026-06-14）
- 相关：[architecture.md §3](../architecture.md)、[project.md §13](../project.md)

## 背景

导播和主持人权限完全不同：导播拥有最高控制权（开关远程、强制锁、选窗、兜底翻页），
主持人只能在被允许时做受限操作（看画面、点击、翻页、本地锁）。导播 GUI 在 Tauri 窗口内，
主持人在局域网浏览器里。问题是：导播端的 UI 应当怎样与 Rust 后端通信？若所有操作都走同一套
局域网 HTTP API，则导播的特权接口也暴露在网络上，必须额外小心地按 localhost/token 隔离。

## 决策

**两条通道映射两个信任级别**：

- 导播端**本机特权操作**走 **Tauri IPC**（`commands.rs`）：不监听网络端口，不可被局域网访问。
- 主持人端**受限能力**走 **Axum HTTP/WS**（`routes.rs`），是唯一对局域网暴露的面，逐请求校验 token。

Axum 层只依赖 `Arc<AppState>`、不引用 `tauri`，与 GUI 解耦（另见 [ADR-0004](0004-cfg-windows-native.md)）。

## 影响

**正面**
- 攻击面最小：网络上能调用的接口 = 主持人被允许做的事；导播特权天然不在网络上。
- 安全边界由"通道"自然表达，无需在一套 API 上做复杂的来源/权限分流。
- 服务层与 Tauri 解耦，可独立编译与测试。

**负面 / 代价**
- 存在"两个前端 + 两套调用方式"，导播 GUI 与主持人页不共享通信代码。
- 同一能力（如翻页）在 IPC 与 HTTP 各有入口，需保持语义一致。

## 备选方案

- **Tauri 当壳、全走 HTTP**：导播页也加载 Axum serve 的 SPA，统一一套前端/通道；
  但导播特权接口要谨慎绑定 127.0.0.1，安全边界不如本方案天然 —— 否决。
- **不用 Tauri、纯 Rust 托盘 + 浏览器**：最简单，但导播端没有真正的应用窗口，
  与 [project.md §5.2](../project.md) 期望的"像正经 Windows 应用"相悖 —— 否决。
