# 宏异常处理与日志修复

用户反馈：手机点击宏后显示断开，导播日志没有记录；部分现场出现 VBA 运行时错误 91。

## 已确认的代码问题

- 宏调用对任意失败执行无参回退，无法证明宏体尚未运行，存在重复执行风险。
- IDispatch::Invoke 没有接收 EXCEPINFO，丢失 VBA 异常来源、说明和错误码。
- 宏日志只在阻塞调用返回后写入，弹窗期间没有开始记录。
- 手机心跳与 PPT 查询使用同一个 Promise.all；PPT 查询阻塞会拖住连接状态。
- 导播 PPT 查询使用同步 IPC；导播日志也需要等待其他状态查询一起返回才刷新。

## 修复行为

仅 DISP_E_BADPARAMCOUNT 允许无参回退；运行时异常、忙碌和未知错误不自动重跑。
记录调用开始、形状和宏名、回退原因、成功/失败、耗时、COM 异常详情。
宏及远程翻页/黑屏调用在后台执行，8 秒后返回“结果未知”的超时提示。
超时不会取消 COM，也不会释放执行许可；直到原调用返回，其他受保护调用不会排队堆积。
原调用迟到的完成结果仍然写日志。
HTTP 和 IPC 的 PPT 查询共用忙碌保护，查询最多等待 2 秒。
手机心跳独立于 PPT 查询，宏 500/超时/网络错误显示提示；导播日志独立更新。

## 验证

自动测试覆盖心跳与阻塞 PPT 查询隔离、宏 HTTP 错误提示、导播日志独立刷新、
回退错误分类、超时后仍持有许可、迟到结果日志，以及忙碌时 HTTP 心跳正常而新宏被拒绝。
需要通过 Linux workspace 测试、前端测试/类型检查，以及 Windows 交叉编译。

Windows 实机复测：

1. 分别测试无参宏与 `Sub Handler(shp As Shape)`，检查宏名和执行结果日志。
2. 在测试演示文稿内执行主动报错 91 的宏，确认没有第二次自动执行。
3. 保留 VBA 弹窗超过 8 秒：导播日志应有开始和超时；手机心跳仍可用。
4. 弹窗未关闭时再发宏请求，应提示忙碌；关闭后应记录原调用最终结果。
5. 对 LAN 和 Relay 各执行一次上述步骤，并检查强制锁仍可使用。

限制：应用不能修复模板 VBA 中未初始化的变量，也不能安全终止正在执行的 COM 调用。
异常详情只能在 PowerPoint 将异常返回 COM 后获取；弹窗期间先记录开始/超时信息。
日志仍是当前进程的内存环形缓冲，关闭应用前应保留需要的记录。
